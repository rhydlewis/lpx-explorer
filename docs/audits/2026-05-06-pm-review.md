# UX Review — lpx-explorer (Product Manager)

Date: 2026-05-06
Reviewer: Product Manager agent (read-only review of code + BRIEF.md + TASKS.md + Python reference at `lpx-toolkit/inspector-mockup.html`)

## Biggest UX risk (lead)

**The compatibility verdict — the entire reason this app exists — is buried as the second section, under a section label "Compatibility" that competes visually with "Project", "Tracks", and "Plug-in Chains".** The headline JTBD per BRIEF.md is *"Will this project open cleanly on this Mac?"* That answer should be the screen, not a row in a stack of equally-weighted sections. Today, a user opens a `.logicx`, sees a project name, sees a metadata grid of similar weight, and has to *read* to find the verdict. For the one question that determines whether they need to act, that's a regression vs. a CLI's bolded `MISSING (3)` line.

## Must fix

**1. Verdict is not the hero.** The whole UI is organised around the parser's data model (project → tracks → plug-ins) rather than the user's question (will it open?). Trade-off: making the verdict hero pushes the metadata grid down — but a working musician opens this app *because* they suspect a problem, not to admire BPM. **Fix:** Promote the verdict to a sticky banner under the project name with verdict-state colour (green/amber/red), the missing count, and the one CTA that matters ("Show 3 missing plug-ins" → focuses the rail). Demote `Compatibility` as a section label.

**2. "AU registry not yet scanned" is a dead-end on first launch.** New users will hit the inspector before they've ever run an AU scan. The compatibility section shows a grey pill that's only sometimes followed by a "Run AU scan" button (only when status is `absent`, not `idle`/`loading`). They'll see a verdict-shaped placeholder with no obvious next action. **Fix:** Auto-trigger the AU scan on first launch (with progress in the empty state), or make "Run AU scan" the primary CTA in the EmptyState — *before* "Pick project" is even useful.

**3. Synthesised fingerprints leak into the UI.** `PluginRail`'s second line shows `aufx/dela/appl`-style fingerprints next to registry-matched names. A musician shouldn't need to know what a 4CC is. The codebase already knows this (Apple stock plug-ins suppress the second line — comment at `PluginRail.tsx:54-65`), but every non-Apple match still shows it. **Fix:** Hide the fingerprint by default; expose it under a "Show technical IDs" toggle or row hover-tooltip for the power user who's debugging an auval mismatch.

## Should fix

**4. No "what do I do about a missing plug-in" affordance.** The verdict says "3 missing" and the rail flags `Missing on this Mac`, but there's no path forward — no manufacturer, no Plugin Alliance / Native Instruments link, no copy-fingerprint, nothing. **Fix:** On a missing row, expose a small action menu — *Copy fingerprint*, *Search the web for "[name]"*, eventually *Open Plugin Manager*. Even a copy-button is a 1-day win.

**5. Track Registry and Plug-in Chains overlap conceptually.** A user sees two track-shaped sections back-to-back with different completeness levels and no explanation of why one is named "Tracks" and the other is "Plug-in Chains". The "(N identified)" coverage gap notes are a parser-mental-model leak. **Fix:** Merge into one Tracks list. Put inserts as a disclosure under each row (you already do this in `TrackRow`). Drop the registry vs chains distinction from the user-facing layout — that's an implementation seam.

**6. EmptyState undersells the value prop.** "Inspect Logic Pro projects without opening Logic" is accurate but doesn't surface the JTBD. **Fix:** Lead with "Check whether a project will open before you launch Logic" — the actual job. Add a third tertiary CTA: *Drag a `.logicx` here* (the drop handler exists, the affordance doesn't).

**7. ProjectInfo grid has no scannable hierarchy.** Key/BPM/Sig/SR/Frame rate/Tracks/Created/Modified/Size/Audio files all have equal visual weight. The musically meaningful triplet (Key · BPM · Sig) wants to be one big readable line at the top of the inspector, the way it's done in the original `lpxtool.png` mockup. **Fix:** Hoist Key · BPM · Sig into the project header beside the title.

## Nice to have

**8. No global search / command palette.** Once a user has a folder with 50 projects, finding "the one with Serum on a Tuesday" is the next obvious job. LibrarySearch exists at the rail level — extend it to span fingerprints and plug-in names across the whole library.

**9. Reveal in Finder is the only project-level action.** No "Copy path", no "Open enclosing folder", no "Show in macOS Quick Look". These are 5-minute additions that make the app feel native.

**10. "Show all" toggle on Plug-in Chains has no explanation of what "all" means.** The aria-label hides the tradeoff inside accessibility metadata. **Fix:** Replace with a label like "Include routing tracks (buses, aux, output)" — the longer label is clearer than the cryptic toggle.

## Backlog reality check

From the code's TODO references:

- **`lpx-explorer-14d` (NSKeyedArchive-blob track recovery)** is referenced as the cause of the "(N identified)" gap. Consider whether *closing the gap* is actually a higher priority than *hiding the gap from non-technical users*. The gap message is a parser apology that most users don't need.
- **No backlog item addresses the "what do I do next?" flow for missing plug-ins.** That's the hole in the JTBD — the app diagnoses the problem and stops. A "missing plug-ins → search/copy/help" affordance is the highest-leverage feature the app doesn't have.
